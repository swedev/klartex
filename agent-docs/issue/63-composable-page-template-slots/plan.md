# Plan: Issue #63 — Composable page templates: separate header and footer slots

## Goal

Restructure the page-template surface around two slots, **header** and **footer**. Each slot independently picks either a predefined variant or custom `.tex.jinja` source. Structured settings keep applying to any slot that stays predefined; only a custom slot owns its own chrome. The monolithic built-ins dissolve: `formal` / `clean` / `none` differ only in header content, so they become the header slot's predefined variants (org details + logo / logo only / empty), and today's page-number footer (with `\kxfooter` when footer fields are given) becomes the footer slot's predefined variant. The old names stay accepted as aliases for the corresponding slot combinations, so every existing payload renders unchanged.

The problem as it exists on `main`, verified before planning:

- `klartex/block_engine.py:60-68` and `klartex/recipe.py:231-236` set `external_page_template = page_template_source is not None`, and when true load `"none"` and discard `data.page_template` entirely — deliberately: a missing or unknown `data.page_template` is tolerated in that mode (CHANGELOG 0.2.1, line 276). `klartex/templates/_page_template_overrides.tex.jinja:7` wraps *every* structured override — `font`, `header_font`, `footer`, `page_numbers`, `first_page_header`, `diff_style` — in `\BLOCK{if not external_page_template}`. A custom source is all-or-nothing.
- The three built-ins in `klartex/page_templates/` each carry both slots: `formal.tex.jinja` (org-details + logo header, `\doctitle • Sida x av y` footer), `clean.tex.jinja` (logo-only header, `Sida x av y` footer), `none.tex.jinja` (unconditional header-space reclaim, `Sida x av y` footer). The footer is duplicated three times; the header-space reclaim (`\geometry{top=2cm, headheight=0pt, headsep=0pt, includehead=false}` + `\fancyhead{}`) is duplicated with three different conditions.
- The `\providecommand` contract (`\orgname`, `\orgaddress`, `\orgwebsite`, `\orgemail`, `\orgphone`, `\brandlogo`) lives inside `formal.tex.jinja` (all six), `clean.tex.jinja` (`\brandlogo` only) and `_recipe_base.tex.jinja:5` (`\orgname` only). Nothing structured ever sets these macros — the only way to get text into the `formal` header is to copy the source and add `\renewcommand`s, which is exactly the issue's complaint. Consequence worth stating plainly: on `main`, `page_template: "formal"` without a custom source renders the same as `"none"` (both `\ifdefempty` checks are true, the header space is reclaimed), differing only by the `\doctitle •` prefix in the footer.

The consumer on the other side of this API is `swedev/klartex.se` (`backend/src/klartex_se/render.py:44,134-176`): it keeps `BUILTIN_PAGE_TEMPLATES = {"formal", "clean", "none"}`, passes a built-in name through as `data.page_template`, and for a registered bundle reads `<bundle>/page_template.tex.jinja` and passes it as `page_template_source` with `asset_dir=bundle_dir`. Its template editor is designed slot-centric against this issue (issue text, user decision 2026-08-29). Nothing there is changed by this plan; the follow-up in that repo is noted under Risks.

## Approach

### Provenance summary

- **User decisions (issue #63, #64, #67 bodies, origin "template-editor design 2026-08-29"):** two slots, header and footer; each slot is predefined-or-custom; structured settings keep applying to predefined slots; the built-ins become header variants; the standard footer becomes the footer variant; `formal`/`clean`/`none` stay as aliases; header variants are named `letterhead` (org details + logo) and `logo` (logo only), and "no header" is the empty slot, not a named variant (#64); page-number policy belongs to the slot that carries the numbers (#67, done there, but the slot shape must leave room for it).
- **Existing conventions (with location):** `\providecommand` contract macros (`klartex/page_templates/formal.tex.jinja:1-6`, README "Egen sidmall"); header-space reclaim geometry (`formal.tex.jinja:38-41`, `none.tex.jinja:1`); `\kxfooter` for the fields footer and its precedence rules (`_page_template_overrides.tex.jinja:17-22`, `_recipe_base.tex.jinja:12-17`); monolithic source tolerates missing/unknown `data.page_template` (`block_engine.py:61-65`, CHANGELOG 0.2.1); LaTeX-safe Jinja delimiters and the escape→restore pattern (`CLAUDE.md`); Swedish schema descriptions, English identifiers (`CLAUDE.md`).
- **Agent judgment (flag in the PR body as open to question):** the JSON shape of a slot (D1), footer fields living directly on the footer slot object (D2), the `title` setting on the standard footer (D3), org fields and logo as structured settings on the header variants, including their names (D4), custom slot sources travelling as `render()` kwargs / CLI flags rather than inline in data (D5), document-level settings applying in every mode including legacy monolithic source (D6), composition order (D7), moving the `\providecommand` contract into `klartex-base.cls` (D8), `null` for the empty slot (D9), non-slot defaults derived from the resolved slots (D10).

### The slot model

**D1 — slot value shape.** A slot is one of:

| JSON value | Meaning |
|---|---|
| omitted | the engine default (block engine: header empty, footer `standard`; recipes: header `letterhead`, footer `standard` — same defaults as today's `none` / `formal`) |
| `null` | the empty slot (no chrome in that position) — D9 |
| `"<variant>"` | a predefined variant with default settings |
| `{"variant": "<variant>", ...settings}` | a predefined variant with settings |

Header variants: `letterhead`, `logo`. Footer variants: `standard`. The header object form **requires** `variant` (the two variants accept different settings, so the schema is a `oneOf` per variant and needs the discriminator). The footer object form **may omit** `variant` and then means `standard` — that is what keeps every existing `footer: {company: …}` payload valid (D2). Custom source is *not* expressed in JSON (D5) — it arrives through `render(header_source=…)` / `render(footer_source=…)` and overrides whatever the data says for that slot, the same way `page_template_source` overrides `data.page_template` today.

**D2 — footer fields sit directly on the footer slot object.** Today's `footer: {"company": …, "bankgiro": …}` dict is, unchanged, a valid footer slot object whose `variant` defaults to `standard`. So the old and new forms are the same form; no payload migrates. Reserved keys next to the field names: `variant`, `title` (D3), and — reserved in the loader's key list only, deliberately *not* in the schema until #67 defines its tri-state — `page_numbers`. `SlotSpec` exposes `fields` (settings minus reserved keys) and `has_fields`, and only `has_fields` decides whether `\kxfooter` is emitted — so a `formal` footer whose settings are just `{"title": True}` renders the page-number line, never an empty `\kxfooter`. Alternative considered: nesting fields under `footer.fields` — cleaner separation, but breaks every existing `footer` payload (`tests/test_renderer.py:616-652`, faktura/kvitto docs) for no user-visible gain.

**D3 — `title` on the standard footer.** `formal`'s footer prints `\doctitle\ \textbullet\ ` before the page number; `clean`'s and `none`'s do not. One footer variant must cover both without changing any alias's output, so `standard` gets a boolean setting `title` (default `false`); the `formal` alias sets it to `true`. Only affects the small page-number line — `\kxfooter` (fields present) never printed the title and still does not.

**D4 — structured org fields and logo on the header variants.** Without them the predefined header variants are hollow (see Goal: `formal` renders like `none` on `main`). `letterhead` accepts `org_name`, `address`, `web`, `email`, `phone`, `logo`; `logo` accepts `logo`. Names follow the footer's existing field names where the concept coincides (`address`, `web`, `email`, `phone` — `web` maps to the `\orgwebsite` macro); `org_name` rather than `company` because the header macro is `\orgname` and the contract is org-shaped, not company-shaped. The composition emits `\renewcommand{\orgname}{…}` etc. for each given field, so the fragments keep reading the contract macros — a custom source that `\renewcommand`s them still works, and the geometry-reclaim check stays a single `\ifdefempty` test at the LaTeX level. `logo` is a file name resolved the way faktura's `logo` is today (`TEXINPUTS` / `asset_dir` / cwd; see the Risks note on escaping). The field *names* are this plan's own call — #64 settles variant names and presentation, not these — so say so in the PR body.

**D5 — custom sources via API kwargs and CLI flags, not inline JSON.** Two reasons: `escape_data()` escapes every string in the payload and raw LaTeX would need the same restore treatment as `latex.source` (`renderer.py::_restore_block_types`), and keeping LaTeX out of the validated JSON keeps `klartex schema _block` purely structured and the trust boundary where it is today (`page_template_source` is not data). `render()` grows `header_source: str | None = None` and `footer_source: str | None = None`; `page_template_source` stays and means "one source for both slots" (legacy monolithic). Passing `page_template_source` together with either slot source raises `ValueError`. CLI: `--header-template FILE` / `--footer-template FILE`, mutually exclusive with `--page-template`; both files must live in the same directory (that directory becomes `asset_dir`), otherwise exit 1 with a message. Auto-detection (`<stem>.tex.jinja`, `page_template.tex.jinja`) is unchanged and stays monolithic, and — like `--page-template` today (`cli.py:91-101`) — an explicit slot flag suppresses it entirely, so a `page_template.tex.jinja` lying in cwd next to `--header-template` is ignored rather than tripping the mutual exclusion.

**D6 — document-level settings apply in every mode.** `font`, `header_font` and `diff_style` are not chrome: `font` is `\setmainfont`, `header_font` redefines the `\kxheaderfont` hook (which a custom fragment may or may not consume), `diff_style` is inline-markup styling. They are emitted first, before any slot, so a custom source that sets its own `\setmainfont` wins. Slot-level settings (`first_page_header` → header; `page_numbers`, footer fields, `title` → footer) apply only when that slot is not custom. Behaviour change for one combination: a payload that sends a monolithic `page_template_source` *and* `font`/`header_font`/`diff_style` in `data.page_template` — those keys were silently dead and now take effect. Called out in the CHANGELOG.

**Monolithic mode keeps its tolerance.** With `page_template_source`, the loader does *not* alias-resolve `data.page_template`: a missing value, an unknown string (`"bogus"`), or an object with an unknown `name` all pass the loader. From an object, only the document-level keys (`font`, `header_font`, `diff_style`) are read; `name`, `header`, `footer`, `page_numbers`, `first_page_header` are ignored. What reaches the loader is path-dependent and unchanged from `main`: the block engine's schema types `name` as a free string, so `render("_block", …)` with an unknown name and a monolithic source renders (the 0.2.1 guarantee); every recipe schema constrains `name` to the three aliases with an `enum`, so `render("protokoll", …)` with `page_template: "bogus"` fails validation on `main` and keeps failing — the tolerance tests therefore cover the loader and the block path only. Per-slot sources are different: the *other* slot still resolves from the data, so an unknown alias or variant there raises as usual.

**D7 — composition order** (one Jinja include, `_page_template.tex.jinja`, replacing `\VAR{page_template_source}` + `_page_template_overrides.tex.jinja` in both meta-templates):

1. document-level settings (`\setmainfont`, `\kxheaderfont`, `\kxdiffstyle`)
2. header slot: custom source verbatim, or the variant fragment preceded by `\renewcommand`s for its settings, or nothing
3. footer slot: custom source verbatim, or the `standard` fragment (`\kxfooter` when `has_fields`, else the page-number line honouring `page_numbers` and `title`), or nothing
4. header-space reclaim: empty slot → unconditional; `letterhead` → `\ifdefempty{\orgname}{\ifdefempty{\brandlogo}{reclaim}{}}{}`; `logo` → `\ifdefempty{\brandlogo}{reclaim}{}`; custom → nothing (the source owns its geometry)
5. `first_page_header: false` (header not custom — predefined *or empty*) → `\fancypagestyle{plain}{…}\thispagestyle{plain}` as today. The empty case matters for the goldens: on `main`, `none` defaults `first_page_header` to `false` and therefore emits this block (`_page_template_overrides.tex.jinja:25-28`); D10 keeps that default, and the guard must let it through.

The reclaim moves to step 4 because it is a preamble-time `\ifdefempty` test: a custom footer source (step 3) may `\renewcommand{\orgname}`, and the test must see the final value. Contract-macro definitions are last-writer-wins in emission order (settings → header source → footer source); document that a custom source should not touch the other slot's `\fancyhead`/`\fancyfoot` cells. The recipe path's own `data.footer` (faktura/kvitto) keeps being emitted *after* the include, so it keeps winning over both a predefined and a custom footer slot exactly as today (`_recipe_base.tex.jinja:12-17`).

**D8 — the contract lives in `klartex-base.cls`.** Six `\providecommand`s (`\orgname`, `\orgaddress`, `\orgwebsite`, `\orgemail`, `\orgphone`, `\brandlogo`) move from `formal.tex.jinja` / `clean.tex.jinja` / `_recipe_base.tex.jinja:5` into the class, next to `\kxheaderfont`. Any slot — predefined or custom, either path — can then rely on them, and the README's `\providecommand{\orgname}{}\renewcommand{\orgname}{…}` idiom keeps working. Risk: a custom source that uses `\newcommand{\orgname}` on the block-engine path (where nothing predefined it before) now errors "already defined". The recipe path already had this property for `\orgname`, and the documented idiom is `\providecommand` + `\renewcommand`; note in the CHANGELOG.

**D10 — non-slot defaults derive from the resolved slots, not from an alias table.** `page_numbers` defaults to `true`; `first_page_header` defaults to "the header slot is not empty" (`none` → `false`, as today's table says; `formal`/`clean` → `true`). Explicit keys override. This is what makes `"formal"` and `{"header": "letterhead", "footer": {"title": true}}` resolve to the same `PageTemplate`, so the alias-equivalence tests hold without the object form silently inheriting `none`'s `first_page_header: false`.

**What stays put.** `PageTemplate.footer_has_payment` (used by `_recipe_base.tex.jinja:190`), `page_numbers` and `first_page_header` as top-level booleans (#67 and #66 move/retire them; this plan only scopes them to their slot), `list_page_templates()` (returns the three aliases as before, for `klartex.se`), `read_page_template_source(alias)` (now returns the *composed* source for the alias so "copy the built-in and edit" keeps working — one small helper composes the alias's two fragments plus the reclaim block), the `\kxfooter` layout (#62), margins (#65), title-page chrome (#66), auto-detection in the CLI.

## Risks

- **Output drift on the alias set.** The whole point is "existing payloads render unchanged", and the three built-ins are being cut into fragments and re-emitted through Jinja. Two locks: the goldens captured from `main` before any change (steps 0 and 14 — line-set equality plus explicit ordering assertions), and the text-layer checks (step 19). The alias-vs-slot equivalence tests (step 17) only show the two spellings agree; they are not the compatibility proof. Before opening the PR, also diff the composed preamble of each alias against `git show main:klartex/page_templates/<alias>.tex.jinja` by eye.
- **`\ifdefempty` timing.** The reclaim test runs at preamble time. Because settings emit `\renewcommand`s *before* the fragment and the reclaim block runs *after* both slots, every path that defines a contract macro precedes the test. A custom source that defines `\orgname` inside `\AtBeginDocument` would still be missed — same as today; document "define contract macros at preamble top level".
- **Escaping of `logo` file names.** `escape_data()` turns `my_logo.pdf` into `my\_logo.pdf`, which `\includegraphics` cannot open. Faktura's `logo` has the identical limitation today (`_recipe_base.tex.jinja` `header_logo`), so this plan mirrors it and documents "use file names without LaTeX-special characters" in the schema description. Fixing it properly (restore `logo` from the unescaped payload, as `_restore_block_types` does for `latex.source`) is a separate issue for both fields — file it only if the user agrees.
- **Recipe `page_template` string path.** `recipe.py:168-175` renders `document.page_template` as a Jinja expression only when `data.page_template` is not a dict. A dict without `name` must still get the recipe's default (`formal`) — step 8 handles it by passing `default=<rendered string>`. Tested in step 18.
- **`klartex.se` follow-up.** Its `BUILTIN_PAGE_TEMPLATES` set and bundle model keep working through the aliases and `page_template_source` (monolithic tolerance kept). Exposing slot sources (`header_source` / `footer_source`) and the structured header fields in its API and template editor is a follow-up in that repo; do not file it without asking the user.
- **Sequencing with #66 and #67.** Both will edit `first_page_header` / `page_numbers` in exactly the model, schema and composition code this plan creates. Land #63 first; plan #66/#67 against the merged slot model (their issue texts already assume it). `page_numbers` on the footer slot is reserved in the loader (rejected until #67 defines the tri-state) so #67 does not need to unpick anything.
- **Scope pressure from #61/#62/#64/#65.** All reference this issue and the same files. This plan keeps `\kxfooter`'s layout (#62), adds no margins (#65) and no typography knobs (#61), and takes only the variant *names* from #64. The header field names (D4) are this plan's own call — say so in the PR body so #64 can rename before its descriptions are written.
- **Working-tree conflicts.** No other open plan touches `klartex/page_templates*`, `_page_template_overrides.tex.jinja`, the two meta-template headers, or `klartex-base.cls`'s hook area.
