# Plan: Issue #98 — Letterhead columns overflow on a single unbreakable token

## Goal

A long email address or web address in the letterhead header's contact column (`fields.email`, `fields.web`) wraps inside its 0.25\textwidth minipage instead of running out of it over the logo or off the page. The Swedish-association shape from the issue — `styrelsen@bostadsrattsforeningenekbacken.se` — wraps at its separators onto as many lines as it needs (three, in the default geometry), with no `Overfull \hbox` and every glyph inside the column. The #84 guarantees stay: columns wrap at spaces, the organisation name is never hyphenated, and the goldens are unchanged.

## Approach

### State verified before planning

- `klartex/page_templates/header/letterhead.tex.jinja` typesets the contact column as a `[t]{0.25\textwidth}` minipage under `\raggedright\hyphenpenalty=10000`, stacking `\kx@hdrline{\orgwebsite}`, `\kx@hdrline{\orgemail}`, `\kx@hdrline{\orgphone}` (`\kx@hdrline` in `klartex/cls/klartex-base.cls` line 128). `\hyphenpenalty=10000` was added by #84 to stop the organisation name from hyphenating; it also forbids every automatic break inside an address, and an address has no spaces to break at.
- The contact macros have exactly one source. `\orgwebsite`/`\orgemail`/`\orgphone` are only referenced from the letterhead fragment, and their values come solely from `PageTemplate.header_macros` (`klartex/page_templates.py` line 693), which walks `HEADER_VARIANTS["letterhead"].fields` and returns `(macro, value)` pairs that `klartex/templates/_page_template.tex.jinja` (line 28) emits as `\renewcommand{\<macro>}{<value>}`. The recipe path and the block path both go through it. The value is already LaTeX-escaped (`escape_data` ran before slot resolution), so `_` in an address arrives as `\_`. The footer's fields take a different route (`footer_keyvals`, line 1005) and are not touched by anything in `header_macros`.
- The escape table (`klartex/tex_escape.py::_REPLACEMENTS`) never produces `@`, `.` or `/`, so inserting a break opportunity after those characters in the escaped string cannot split an escape sequence.
- `\exhyphenpenalty` is untouched, so an explicit `-` in a hostname is already a break point; only `@`, `.` and `/` need help.
- Measured in the real renderer (block engine, default geometry: A4, `\kxsidemargin` 3cm, so `\textwidth` = 595.28 − 2·85.04 = 425.20pt; the contact column spans x = 85.04 + 0.33·425.20 = 225.36 to 85.04 + 0.58·425.20 = 331.65pt, i.e. 106.3pt wide):
  - Unpatched, the issue's email is one word with `xMax` = 368.70 — 37pt past the column edge, and xelatex logs `Overfull \hbox`.
  - With `\allowbreak{}` after each run of `@`/`.`/`/`, it renders as `styrelsen@` / `bostadsrattsforeningenekbacken.` / `se`, every `xMax` ≤ 329.02. `www.bostadsrattsforeningenekbacken.se` gives `www.` / `bostadsrattsforeningenekbacken.` / `se`; `https://www.bostadsrattsforeningenekbacken.se/styrelsen` gives `https://www.` / `bostadsrattsforeningenekbacken.` / `se/styrelsen`.
  - The widest segment, `bostadsrattsforeningenekbacken.` (31 characters), measures 103.7pt of the 106.3pt column at 6pt. A separator-free label only a few characters wider still overflows: a break-based fix has that ceiling by construction (D5).
  - Header growth is vertical in both directions around the head baseline. With address (1 line), a three-line `web`, a three-line `email` and a phone — seven contact lines — the topmost header glyph sits at y = 29.1pt from the paper edge and the last contact line ends at y = 88.8, 9.5pt above the body's first line at y = 98.3. Seven lines is therefore the practical ceiling in the default geometry; fancyhdr's `\headheight is too small` warning is logged but does not fail the run (the renderer halts on errors only). See D6.
- The two goldens that include the letterhead (`tests/fixtures/golden/page_template_faktura.tex`, `page_template_letterhead_title.tex`) carry no `\renewcommand{\orgemail}`/`\orgwebsite` — their payloads set no contact fields — so a change in how those values are emitted leaves the goldens untouched. The fragment itself is not changed.
- `tests/test_pdf_text_layer.py::_word_box` (line 280) parses `pdftotext -bbox` for one named word on the first page and returns `(xMin, yMin)`; the `_WORD_BOX` regex already captures `xMax`/`yMax` positions but discards them. `_PT_PER_CM` is the only geometry constant there. `tests/test_page_templates.py` line 475 already asserts on `header_macros`, so the Python-side transformation has a unit-test home. `tests/test_schemas.py` largely strips descriptions, so a description change needs its own assertion.

### Provenance

- **User decision** (issue #98): the overflow is a defect to fix; the issue explicitly says the direction "needs a small design decision" and lists three candidates (breakability, font scaling, truncation with a warning).
- **Agent judgment, open to question**: which candidate (D1), where the mechanism lives (D2), which characters break (D3), scope (D4), the residual horizontal case (D5), vertical growth (D6). All bounded — a wrong choice is visible in the rendered header and reversible in a follow-up PR; nothing is stored, published or contractual. `fields.email`/`fields.web` remain plain strings in the schema, so nothing about the JSON surface changes.

### Design decisions

- **D1 — Fix by break opportunities, not scaling or truncation (agent judgment).** Options: (a) let the address break at its separators; (b) scale the column font down for overlong tokens; (c) truncate with a warning. Decision: (a). Consequence if wrong: an address that wraps where the reader would rather see it smaller — cosmetic, fixed by a follow-up. Rationale: (a) keeps the address complete and legible at the design size and is what every mail client and the `url` package do; (b) needs a measure-and-shrink loop in the header and produces unreadable text at 4–5pt; (c) destroys the one value a reader needs to copy. What would make (b) right: a user preference for a strictly one-line contact column.
- **D2 — Insert the breaks in Python, at the `header_macros` choke point, driven by a flag on `Field` (agent judgment).** Options: (a) a LaTeX macro in `klartex-base.cls` that walks the token character by character (`\@tfor`-style) and emits `\allowbreak` after separators; (b) a Python transform applied when `header_macros` builds the `(macro, value)` pair, declared per field in the slot model. Decision: (b): `Field` gains `breaks_after: str = ""` (the separator characters after which a break is allowed), set to `"@./"` on the letterhead's `web` and `email` fields; `header_macros` applies `allow_breaks(value, field.breaks_after)`. `breaks_after` is honoured by `header_macros` only; `footer_keyvals` does not read it (D4). Consequence if wrong: the mechanism is moved into LaTeX later — one function and one flag to delete. Rationale: (a) must handle escaped sequences (`\_`, `\textbackslash{}`) and XeTeX's UTF-8 tokenisation inside a `\renewcommand` argument and is hard to unit-test; (b) is a one-regex pure function, follows the established "everything derives from the field table" convention (CLAUDE.md, Page templates), is unit-testable without TeX, and is available to another field by declaring it. `\allowbreak{}` rather than `\allowbreak ` so the following character is never swallowed as a macro-name delimiter. `\allowbreak` (`\penalty0`) adds no hyphen character, so the break is invisible except for the line change — consistent with #84's no-hyphenation header.
- **D3 — Break after each maximal run of `@`, `.` or `/`, never at the end of the value (agent judgment).** Options: after every character (`seqsplit`-style); after each separator character; after each run of separators. Decision: after each run: `re.sub(r"[@./]+(?=[^@./])", lambda m: m.group(0) + r"\allowbreak{}", value)` — the lookahead requires a non-separator to follow, so the regex cannot backtrack into a trailing run (`(?!$)` would turn a trailing `//` into `/\allowbreak{}/`). So `https://` stays whole (a break between the two slashes would leave `https:/` on a line) and a value ending in `.` or `//` gets no insertion at all. Consequence if wrong: a token with another separator (`?`, `=`, `:`) still overflows — the set is one string in the field table. Rationale: `@`, `.`, `/` are the separators the issue's example and any web/email address carry; `-` already breaks through `\exhyphenpenalty`; breaking anywhere would split `bostadsrattsforeningen` mid-word, which #84's `\hyphenpenalty=10000` exists to prevent in this column.
- **D4 — Scope: the letterhead's `web` and `email` fields only (agent judgment).** Options: also flag `phone` and the organisation column; also the columns footer's `email`/`web`. Decision: letterhead `web` + `email`. `phone` has spaces or hyphens and breaks already; `org_name`/`address` must not break inside a word (#84). The footer's contact column is wider, not under `hyphenpenalty=10000`, and goes through `footer_keyvals`, which would need to apply `allow_breaks` too (a one-line change) and would move the faktura goldens — it is the natural follow-up, not what the issue reports. Consequence if wrong: a second, mechanical PR.
- **D5 — The residual horizontal case (a single separator-free segment wider than the column) is accepted, not clipped, scaled or rejected (agent judgment).** Options: leave it; clip the minipage; fail validation above N characters; emit a warning. Decision: leave it, and say "may wrap after @, . and /" in the field descriptions rather than promise containment. Consequence if wrong: a domain label a few characters longer than the issue's 30-character one still overruns — the same behaviour as today for a narrower, but real, class of input (the measured headroom is 2.6pt). Rationale: the issue names the realistic case and the fix solves it; a validation limit or a scaling fallback would be a contract or layout decision the issue did not ask for. What would make a limit or fallback right: a producer that feeds arbitrary user-typed strings into the header, or a real payload that hits the ceiling.
- **D6 — Vertical growth of the contact column is accepted within the measured ceiling and locked by a test (agent judgment).** Options: accept; grow `\headheight` dynamically; scale the font when the column exceeds N lines; cap wrapping. Decision: accept. Seven contact lines — the worst realistic combination (three-line `web`, three-line `email`, phone) — stay on the page and clear the body by 9.5pt in the default geometry; more than that is not a realistic letterhead. The render test (step 4) pins that combination: every header word has `yMin > 0` and `yMax` below the body anchor's `yMin`. Consequence if wrong: a header taller than seven lines touches the body text — visible, and the follow-up is a `\headheight` adjustment in the fragment. Rationale: the issue is horizontal overflow; dynamic header height is its own geometry decision (`margins.top` and the reclaim logic key off `HEADER_BAND_BOTTOM`, see CLAUDE.md) and belongs in a separate issue if a real payload needs it.

### Out of scope

- Changing the fragment's column widths or font size (settled by #84).
- Footer contact fields (D4) and dynamic header height (D6) — follow-up issues if wanted.
- CHANGELOG entry — written at release time per the release flow, not in the PR.

## Steps

1. **Slot model** — `klartex/page_templates.py`: add `breaks_after: str = ""` to `Field` with a doc comment ("characters after which the rendered value may break onto the next line; empty means the value is emitted verbatim; read by `header_macros`"). Add a pure function `allow_breaks(value: str, after: str) -> str` next to the field model: unchanged for an empty `after`, otherwise the D3 regex built from `re.escape(after)`. Set `breaks_after="@./"` on the letterhead's `web` and `email` fields and extend their descriptions with one clause ("a long address may wrap after @, . and /"). In `header_macros`, emit `(typ.macro, allow_breaks(fields[name], typ.breaks_after))`.
2. **Unit tests** — `tests/test_page_templates.py`: `allow_breaks` inserts `\allowbreak{}` after each run of listed characters (`https://` → one insertion), inserts nothing into a trailing run — neither after a final `.` nor inside a final `//` (`https://` on its own stays verbatim), leaves other characters and existing escape sequences (`\_`, `\%`) intact, and is the identity for an empty `after`; `header_macros` for a letterhead with a long email and web returns the annotated values while `org_name`, `address` and `phone` are verbatim; the `LOGO` field (no `breaks_after`) is unchanged (extends the existing test at line ~475).
3. **Schema description test** — `tests/test_schemas.py` (or `test_page_templates.py` next to the other `page_template_schema()` tests): the generated `letterhead` field schema's `web` and `email` descriptions contain "may wrap after". The existing structure tests strip descriptions, so this is the only thing proving the guidance reached `klartex schema`.
4. **Render test** — `tests/test_pdf_text_layer.py`: add `_word_boxes(pdf) -> list[tuple[float, float, float, float, str]]` (all first-page words, `xMin, yMin, xMax, yMax, text`) and keep `_word_box` as a thin wrapper over it. Add module constants for the default geometry (`_A4_WIDTH_PT = 595.276`, `_SIDE_MARGIN_PT = 3 * _PT_PER_CM`, and the contact column's right edge = `_SIDE_MARGIN_PT + 0.58 * (_A4_WIDTH_PT - 2 * _SIDE_MARGIN_PT)`, with a comment tying 0.30 + 0.03 + 0.25 to the fragment). Then a `@requires_tools` test, parameterized over the issue's email, `www.bostadsrattsforeningenekbacken.se` and `https://www.bostadsrattsforeningenekbacken.se/styrelsen` (each in its own field, `email` or `web`), rendering the block engine with the letterhead and the `Ankarord` body anchor: header words are those with `yMin` less than the anchor's `yMin`; assert every header word's `xMax` ≤ column right edge + 0.5, and that the contact words' text joined without spaces equals the address (the break landed at separators only). A second test for D6 sets the three-line `web`, the three-line `email`, an `address` and a `phone` together and asserts every header word has `yMin > 0` and `yMax < anchor yMin`. No negative control is needed: the unpatched email measures `xMax` 368.7 against a 331.7 edge, so the first assertion fails on `main`.
5. **Golden check** — `pytest tests/test_block_engine.py::TestPageTemplateGoldens tests/test_renderer.py::test_faktura_preamble_unchanged_from_golden`: no golden changes expected (no contact fields in those payloads); if one changes, the mechanism leaked outside `header_macros`.
6. **Docs** — `README.md` (the letterhead field notes around line 185) and `README.en.md`: one sentence that `web` and `email` may wrap after `@`, `.` and `/` in the header. `CLAUDE.md`, Page templates section: extend the sentence describing what a `Field` carries with `breaks_after` and that `header_macros` applies it. Written in now-state.
7. **Full suite** — `pytest -rs -n auto`; confirm no xelatex-tagged or `test_server` test is skipped. Manual check per the Test Plan.

## Risks

- **A break lands in an awkward place** (`www.` alone on a line, as measured). Accepted by D1/D3 as cosmetic; `\raggedright` keeps the lines unstretched so no #84-style over-stretching returns.
- **The 2.6pt horizontal headroom (D5).** A label slightly longer than the issue's still overflows; the field description says "may wrap", and the test pins the issue's case, not a guarantee.
- **Vertical growth (D6).** Seven lines is the ceiling in the default geometry; a custom `margins.top` or a payload with four long lines in `web` could exceed it. The D6 test pins the realistic worst case; anything beyond is a follow-up.
- **`\allowbreak{}` in a value reused elsewhere.** Today the contact macros are only read by the letterhead fragment; a custom `header_source` that `\renewcommand`s them bypasses `header_macros` and is unaffected. A future variant that prints the same field inside a `\url`/hyperlink target would not set the flag on its field.
- **Bbox tolerance.** `pdftotext -bbox` coordinates are float; use the same `abs=0.5` slack as the margin tests, and compare against the column's right edge computed from the cls geometry, not against the logo.

## Test Plan
