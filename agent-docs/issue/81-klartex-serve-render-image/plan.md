# Plan: Issue #81 — Publish klartex-render:X.Y.Z at each release — a klartex serve compile endpoint

## Goal

The render process becomes a core artifact. Klartex gains a `klartex serve` CLI subcommand exposing a small FastAPI compile endpoint (`POST /render` → PDF, `GET /health`), packaged behind a new `serve` extra, and every release publishes `ghcr.io/swedev/klartex-render:X.Y.Z` — a multi-arch image built `FROM` the same pinned `klartex-base` the release gate tests in, with the release wheel installed. Consumers (swedev/klartex.se#46) pin one version that equals their `klartex==` pin. The reviewed design doc behind this issue lives with the consumer work in swedev/klartex.se#46.

## Approach

### State verified before planning

- **The source to move exists** on klartex.se branch `issue/46-split-backend-render-app` — pin the import to merged commit `3f1b410` (PR klartex.se#65): `render/src/klartex_render/main.py` (FastAPI app, Content-Length middleware, `/health`), `render/src/klartex_render/render.py` (the `/render` router: asset decoding, concurrency semaphore, error mapping with `_BLOCK_ERROR_RE` block-path extraction), and `render/tests/test_render.py` (~35 tests). The later `-r3` branch (PR 0) retires that in-repo service — the code's new home is here.
- **The slot API replaced `page_template_source`.** The moved service calls `render(..., page_template_source=…)`; current core `render()` (`klartex/renderer.py:110`) takes `header_source`/`footer_source` keywords instead (PR #77/#80). The service's request model must be adapted to `header_source` / `footer_source`, per the issue's contract.
- **Sequencing is already satisfied on main.** v0.16.0 was released 2026-08-30 (`154e474`); PR #80 (`remove-page-template-aliases`) merged after it (`a986661`, current HEAD). The next release therefore carries the alias removal, and this issue must land on main before that release so the first image ships with it — one migration for consumers (user decision in the issue body).
- **The base pin to reuse** is `ghcr.io/swedev/klartex-base:20260828-3@sha256:b011056413d449bdc41b893ff1bd538a2be46d78d3794698eb134f45936d6ff2` (`publish.yml` `container.image`).
- **The core's filename pattern is not enough for assets**: `FILENAME_PATTERN` in `klartex/page_templates.py:93` is `^[^\\#$%&_{}~^]+$`, which admits `/` and `..` — confirming the issue's requirement for the stricter `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` on asset names.
- **The base image sets no PATH** (`docker/Dockerfile.base` symlinks `/usr/local/texlive-bin` but leaves PATH to the consumer), and `_compile_tex` locates xelatex via `shutil.which` — so the render Dockerfile must set `ENV PATH`.
- **`.dockerignore` does not exist**, and `pyproject.toml` has no `serve` extra and no `httpx` in dev (FastAPI's `TestClient` requires it). Both `README.md` (Swedish) and `README.en.md` exist and are maintained in parallel.
- **`publish.yml` semantics to respect**: top-level `permissions` include `id-token: write` (for the PyPI publish); the `publish` job is guarded `if: github.event_name == 'release'`; `workflow_dispatch` runs the gate + build only. A job that plainly `needs` a skipped job is itself skipped, hence the `!cancelled()` pattern the issue prescribes.
- **Coordination dependency, not a blocker: #76 (open)** will make `_validate_blocks` raise a structured `BlockValidationError(ValueError)` with a `path` attribute — exactly what the moved server's `_BLOCK_ERROR_RE` parses out of message prose. Since server and core now live in the same package, the server should prefer the structured attribute the moment #76 lands; until then the moved regex (with its tests) is the mechanism. If #76 lands first or together with this, drop the regex and consume `e.path` directly. The regex must not become a reason to keep #76's message text frozen.

### Provenance

- **User decisions (issue #81 body, conversation 2026-08-30):** the core publishes the image, versioned as the core; the contract (endpoint shapes, error types, env-only config, defaults 2 / 80 MB); the 413 is decided **on Content-Length before the body is read** (so it is a declared-size check by design); `workers=1`; default host `127.0.0.1` with `0.0.0.0` only in the image CMD; same base pin as the release gate, guarded equal; wheel-install with `--only-binary=:all:`; multi-arch amd64+arm64; tag `X.Y.Z` only, never `latest`, no overwrites; the image job's `needs`/`if` shape (which deliberately lets the image publish even if the PyPI step failed — both are retryable independently); no rebuilds on base bumps (next release picks it up; urgent → patch release); dispatch is retry-only and refuses when the image tag already exists; tests move to `tests/test_server.py` and run in per-PR CI and the in-image release gate; first image ships in the same release as the alias removal; #51's sandboxing is out of scope.
- **Existing conventions (with location):** error mapping, block-path extraction, semaphore and limits are the reviewed klartex.se service (commit `3f1b410` there); the free-disk step, QEMU/buildx setup, tag validation and digest-to-step-summary pattern come from `.github/workflows/base-image.yml`; version/release flow per `CLAUDE.md` "Releases"; Swedish user-facing docs with a parallel `README.en.md`, English code.
- **Agent judgment (open to question, flag in the PR body):** D1–D7 below.

### Design decisions

**D1 — module layout mirrors the source.** `klartex/server/__init__.py` (docstring only), `klartex/server/app.py` (was `main.py`: FastAPI app, size middleware, `/health`), `klartex/server/render.py` (the router). Keeps the diff against the reviewed klartex.se code reviewable. FastAPI is imported at `klartex.server` module level — the CLI does the lazy import, nothing else imports the package.

**D2 — env config read at import time, module constants kept.** `KLARTEX_MAX_CONCURRENT` → `MAX_CONCURRENT_RENDERS`, `KLARTEX_MAX_BODY_MB` → `MAX_REQUEST_BYTES` (bytes, computed), through a small helper that requires a positive integer and raises a clear error naming the variable on garbage, zero or negative values (`KLARTEX_MAX_CONCURRENT=0` would otherwise silently 503 every request). The moved tests already monkeypatch these module attributes, so import-time reading keeps them working; a server process is started once, so no reload semantics are needed. The Content-Length check is a *declared-size* limit per the issue (chunked or header-less bodies pass it) — stated in the module docstring; the service is an internal compile layer behind a trusting caller, and enforcing a receive-side byte cap is uvicorn/proxy territory, not this issue's.

**D3 — `/health` returns the core version only.** The klartex.se service reported `{"version": service, "klartex": core}` because it was versioned separately. Here there is one version (the issue: "versioned as the core"), so `{"status": "ok", "version": importlib.metadata.version("klartex")}` and the dual-field test is collapsed.

**D4 — release identity, retry, and no-overwrite.** The issue gives the image job `if: ${{ !cancelled() && needs.build.result == 'success' && github.event_name == 'release' }}` and separately says dispatch "exists only as 'retry this same version' and refuses when the tag already exists" — with that `if` a dispatch never reaches the image job, so the two clauses need reconciling. Design (flagged as agent judgment):

- **Version is resolved and validated in the `build` job**, before the artifact is uploaded: read it from the built wheel's filename, require it to equal `pyproject.toml`'s `version`, and on a release event also the tag minus `v`. Exposed as a job output that both `publish` and `image` consume — a mistagged release fails before anything reaches PyPI or ghcr.
- **Image job condition**: `if: ${{ !cancelled() && needs.build.result == 'success' && (github.event_name == 'release' || github.ref_type == 'tag') }}`. The release path is the issue's literal one; the retry path is a `workflow_dispatch` **run from the release tag ref** (Actions runs against the selected ref, so the built code is exactly the released code — a dispatch from `main` after the tag would otherwise rebuild newer code under an old version and is excluded by `ref_type`). On a tag dispatch the guard additionally asserts `github.ref_name == "v<version>"`.
- **No-overwrite guard runs after ghcr login** (an anonymous `imagetools inspect` against a private package cannot distinguish "absent" from "unauthorized"): `docker buildx imagetools inspect ghcr.io/swedev/klartex-render:<version>` — treat only a "manifest unknown"-class failure as absent, fail the job on any other error, and refuse with a clear message when the tag exists. A job-level `concurrency: { group: klartex-render-image-v<version> }` serializes a release run against a concurrent retry so two runs cannot both observe absence and race to push.
- A dispatch from a branch ref keeps today's documented behavior: gate + build run, image job skipped.

**D5 — the serve-extra skip must not be silent.** `tests/test_server.py` opens with `pytest.importorskip("fastapi")` so a contributor without the extra still has a green local suite — but the CI skip-guards only grep `SKIPPED.*xelatex`, and an importorskip reason says "fastapi", so an environment that forgot the extra would silently skip every server test. All three workflows therefore both install `.[dev,serve]` and extend the guard to `! grep -qE "SKIPPED.*(xelatex|test_server)"`.

**D6 — minimal `.dockerignore`.** The image build context is the repo root (so `dist/` is inside); `.dockerignore` excludes `.git`, `agent-docs`, `tests`, `.github`, `.claude`, `.vscode` — the build copies only `dist/*.whl`, so this is hygiene (context upload size, cache stability), not correctness.

**D7 — the error contract is closed; no default 422s.** FastAPI answers a malformed envelope (invalid JSON, missing `template`, non-object `data`, wrong `assets` type) with its default `422` before the endpoint runs, which is outside the issue's documented contract. A `RequestValidationError` handler (and a JSON-decode handler) maps these to the documented `400 {"type": "input_error", "message": …}`, so a caller sees exactly the four documented error shapes plus 413/503. Unexpected extra fields stay ignored (Pydantic default) — the contract is minimal, not strict.

### The pieces

**`klartex/server/`** — moved and adapted:
- Request model: `{"template": str, "data": object, "header_source": str?, "footer_source": str?, "assets": {name: base64}?}` (slot API replaces `page_template_source`; both sources share the 1 MB source limit, each checked separately).
- Assets: max 10, 5 MB each, names validated against `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`, written to a per-request `TemporaryDirectory` passed as `asset_dir` (set whenever a source or assets are given, else `None` so a plain render behaves exactly like the core alone).
- Errors: `400 {"detail": {"type": "input_error"|"validation_error", "message", "path"?}}` with the `_BLOCK_ERROR_RE` block-path mapping unchanged (see the #76 note — swap to the structured attribute when it lands); envelope failures mapped per D7; `413 payload_too_large` on Content-Length before the body is read; `500 render_error` (logged — also the catch-all for `OSError`-class failures while writing assets, wrapped rather than escaping unstructured); `503 overloaded` with `Retry-After: 5`.
- `GET /health` → `{"status": "ok", "version": "<core version>"}`. No docs/openapi/redoc URLs.
- Concurrency: `threading.BoundedSemaphore(MAX_CONCURRENT_RENDERS)`, acquired non-blocking. Envelope, asset and source-size validation happen before the acquire so bad input cannot be starved by busy slots; the core's own schema/block validation runs inside the slot (it is part of `render()`).

**`klartex serve`** — new Typer subcommand in `klartex/cli.py`: options `--host` (default `127.0.0.1`) and `--port` (default `8000`). Lazy import inside the command body, catching `ImportError` only when `e.name` is the missing extra's module (`fastapi`, `uvicorn`, `httpx` chain) → `Error: the serve extra is not installed. Install with: pip install 'klartex[serve]'` and exit 1; any other import failure propagates as the bug it is. Runs `uvicorn.run(fastapi_app, host=host, port=port, workers=1)` — `workers=1` hardcoded, the semaphore assumes one process.

**`pyproject.toml`** — `serve = ["fastapi>=0.115", "uvicorn[standard]>=0.34"]`; add `httpx>=0.27` to `dev` (TestClient).

**`docker/Dockerfile.render`** — `FROM` the exact pin above (comment pointing at the guard); `ARG KLARTEX_WHEEL` (the wheel filename under `dist/`); `COPY dist/${KLARTEX_WHEEL} /tmp/` only — no broad context copy; venv at `/opt/venv`; `pip install --no-cache-dir "/tmp/${KLARTEX_WHEEL}[serve]" --only-binary=:all:` (fails fast if any dependency lacks an arm64 wheel instead of compiling under QEMU); `ENV PATH=/usr/local/texlive-bin:/opt/venv/bin:$PATH` and `PYTHONUNBUFFERED=1`; OCI source/description labels as in `Dockerfile.base`; non-root user created with `useradd --create-home` and `ENV HOME` set explicitly (fontconfig wants a writable HOME; the base's build-time `fc-cache` suffices for rendering, so a tmpfs HOME is fine); `EXPOSE 8000`; `HEALTHCHECK` via `python3 -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health')"` (no curl dependency in the running layer); `CMD ["klartex", "serve", "--host", "0.0.0.0"]`. Nothing in the image writes outside `/tmp` and `HOME` at runtime, so `read_only: true` + tmpfs `/tmp` + tmpfs HOME works — consumers harden their compose (documented in the Dockerfile header, not enforced here).

**`publish.yml`** — `build` job gains the version resolve+validate step (D4) with a job output; new `image` job: `runs-on: ubuntu-latest` (the container-based build job has no docker CLI); `needs: [build, publish]` with the D4 condition; `timeout-minutes: 30`; job-level `permissions: {contents: read, packages: write}` and no `id-token`; job-level per-version `concurrency`; steps: checkout → download `dist` artifact → ghcr login → guard step (tag/ref identity per D4, pin equality between this workflow's `container.image` line and `Dockerfile.render`'s `FROM` line extracted with grep/sed and string-compared, registry-tag absence) → free-disk step copied from `base-image.yml` (two platforms' ~7 GB rootfs under pip hit ENOSPC otherwise) → setup-qemu, setup-buildx → `docker/build-push-action` with `context: .`, `file: docker/Dockerfile.render`, `platforms: linux/amd64,linux/arm64`, `push: true`, `tags: ghcr.io/swedev/klartex-render:${VERSION}`, `build-args: KLARTEX_WHEEL=…` → digest + full pinnable reference to the step summary (the consumer copies it, same pattern as `base-image.yml`). Per the issue's `needs`/`if` shape, a failed PyPI publish does not block the image — each is retryable on its own. Cost lands only at release tagging, per the CI principle. Validate the edited workflow with `actionlint` locally.

**Workflows install the extra** — `ci.yml` (`pip install --break-system-packages .[dev,serve]`), `publish.yml` build job and `base-image.yml`'s in-image run (`pip install ".[dev,serve]"`), all with the extended skip-guard (D5). The server tests are cheap — TeX is already installed in all three.

**`tests/test_server.py`** — the moved suite, adapted: `pytest.importorskip("fastapi")`; `page_template_source` → `header_source` (the inline-bundle tests exercise the header slot; a small `footer_source` case is added); `/health` asserts the core version (D3); the `xelatex`-dependent render tests keep the `needs_xelatex` skip-marker convention so the existing `SKIPPED.*xelatex` guard covers them; new tests for the env-config helper (unset → defaults, valid, zero, negative, non-integer → clear error), the D7 envelope mapping (invalid JSON, missing `template`, non-object `data`, wrong `assets` type → structured `400 input_error`), and the CLI surface (`klartex serve --help` exits 0; the missing-extra error message path via monkeypatched import).

**Docs** — `README.md` (Swedish) and `README.en.md` get a matching short section: `klartex serve` (install via `pip install 'klartex[serve]'`, endpoints, env vars, the security posture pointer) and the `ghcr.io/swedev/klartex-render` image (tag = core version, `0.0.0.0` only in the container). `CLAUDE.md`'s architecture notes gain one paragraph on `klartex/server/` and the image job. CHANGELOG entry is written at release time per the release flow, not in this PR.

### Out of scope

- Everything reachable from a `latex` block inside the container (`/proc/1/environ`, `/etc/hosts`, `/proc/net/*`, sibling temp dirs) — #51's sandboxing scope, per the issue.
- A receive-side byte cap beyond the declared Content-Length check — the issue specifies the check's mechanism; see D2.
- The consumer side — backend as policy layer, compose hardening, `KLARTEX_VERSION` pin, bundle shim: swedev/klartex.se#46.
- Making `ghcr.io/swedev/klartex-render` public: manual, after the first publish — there is no API for package visibility (same trap as the base; documented in swedev/klartex.se#48). Goes in the PR body as a release-day reminder.

## Steps

1. **`pyproject.toml`**: add the `serve` extra (`fastapi>=0.115`, `uvicorn[standard]>=0.34`) and `httpx>=0.27` to `dev`.
2. **`klartex/server/`**: create `__init__.py`, `app.py`, `render.py` from klartex.se's `render/src/klartex_render/` at commit `3f1b410`, adapting: slot API (`header_source`/`footer_source`), env-config helper (D2), core-version `/health` (D3), D7 error handlers, logging namespace `klartex.server`.
3. **`klartex/cli.py`**: add the `serve` subcommand with the narrow lazy-import error, `--host`/`--port`, `workers=1`.
4. **`tests/test_server.py`**: move + adapt the test suite as described; run locally with and without xelatex on PATH to confirm both the render tests and the skip-marker behavior.
5. **CI**: update `ci.yml`, `publish.yml` (build job) and `base-image.yml` (in-image run) to install `.[dev,serve]` and extend the skip-guard to `test_server` (D5).
6. **`docker/Dockerfile.render`** + **`.dockerignore`** (D6): as specified above. Sanity-build locally against the pinned base with a locally built wheel (`python -m build`), run the container, `curl /health` and one `/render`.
7. **`publish.yml`**: build-job version output, then the `image` job (D4 guards, login-before-inspect, per-version concurrency, free-disk, multi-arch build+push, step-summary digest); `actionlint` the result.
8. **Docs**: README sections (both languages), `CLAUDE.md` architecture paragraph.
9. **PR**: body flags D1–D7 as agent judgment, notes the #76 coordination (swap regex → structured path when it lands), carries the release-day reminder (make the ghcr package public manually), and ends with `Closes #81`.

## Risks

- **D4 diverges from the issue's literal `if`** to make dispatch-retry real and safe (tag-ref identity, login-before-inspect, per-version concurrency). Flagged in the PR body; if the user prefers the literal condition, retry falls back to GitHub's "re-run failed jobs" on the release run and the condition reverts to the issue's exact form.
- **First real multi-arch run happens at a release.** The image job can only be fully exercised by a release or a tag-dispatch; the guard's refusal paths can be tested by a branch dispatch beforehand. Mitigation: the job is a thin copy of the proven `base-image.yml` patterns, the first release doubles as the integration test, and a failed image job affects neither the PyPI publish nor retryability.
- **#76 timing.** If it merges while this is in flight, the server's regex consumer should be dropped in the same PR series rather than shipped and immediately deprecated. Cheap either way — the mapping is isolated in `_block_error_path`.
- **`--only-binary=:all:` may refuse a dependency without an arm64 wheel** (uvicorn's `[standard]` extras: uvloop, httptools, watchfiles — all publish aarch64 manylinux wheels today, but a future version might lag). That is the intended fail-fast; the fallback is pinning the offending dependency down or dropping `[standard]`.
- **Semaphore + TestClient concurrency tests can be timing-sensitive** when moved into the parallel suite (`pytest -n auto`); the moved tests use their own semaphores and events rather than sleeps, so they should be robust, but watch for flakes in CI.
- **Two pins must move together from now on**: a base bump PR must update `publish.yml`'s `container.image` and `Dockerfile.render`'s `FROM` in the same commit or the new guard fails the next release. That is the guard doing its job, but it changes the base-bump checklist — noted in both files' comments.
- **File-conflict check against other open plans**: all existing `agent-docs/issue/*` plans belong to merged issues; no active plan touches `publish.yml`, `cli.py` or `pyproject.toml`. No conflicts.
