# Plan: Issue #66 — `title_page` should render a fully chrome-free page (no header, no footer)

## Goal

A `title_page` block makes its own page fully chrome-free — no header, no footer — by itself. Today `\makedoctitle` in `klartex/cls/klartex-titelsida.sty` ends with `\thispagestyle{fancy}`, so the title page carries the header, and the only related knob, `page_template.first_page_header: false`, clears just the header (`\fancypagestyle{plain}{\fancyhead{}\renewcommand{\headrulewidth}{0pt}}` + `\thispagestyle{plain}` in `_page_template.tex.jinja`, step 5) while the footer — page numbers, document title, org fields — stays on page 1. There is no way to get a conventional chrome-free title page.

After this change the behaviour belongs to the block: whoever places a `title_page` gets the expected look without touching the page template. `first_page_header` leaves the API (see D3) — the title-page case is what it existed for, and a header-only flag that ignores the footer has no coherent meaning left.

State on `main`, verified before planning:

- `klartex/cls/klartex-titelsida.sty:36` — `\thispagestyle{fancy}` inside `\makedoctitle`, right before `\newpage`.
- `klartex/templates/_page_template.tex.jinja:46-50` — composition step 5 emits the `plain` redefinition + `\thispagestyle{plain}` when the header is not custom and `first_page_header` is false. fancyhdr's `\fancypagestyle` starts from the fancy fields at use time, so `plain` keeps the footer — exactly the complaint in the issue.
- `klartex/page_templates.py` — `first_page_header` in `DOCUMENT_SETTINGS` (line 634), on `PageTemplate` (line 746), defaulted in `load_page_template` to `not header.is_empty` (lines 1052-1056), and in the module docstring's payload example (line 40). Because the empty-header default is `False`, the block-engine default composition emits the `plain` block today although it has nothing to clear — pinned by `tests/fixtures/golden/page_template_empty_header.tex`.
- Nothing else defines or uses the `plain` page style (`\maketitle`, `titlepage`, `\chapter` are not used), and no recipe renders `title_page` — it is a block-engine-only component (`klartex/components.py:51`, `_block_engine.tex.jinja:178`). `block_engine.py:91` reads the block's `title` for `\setdoctitle`; unaffected.
- The consumer `swedev/klartex.se` does not send `first_page_header` — its code has no reference; only its `llms.txt` and `backend/README.md` mention the key as passed-through documentation (checked read-only in `~/repos/klartex.se`).
- Fixtures with a `title_page`: `tests/fixtures/avtal_block.json` (letterhead header + `pagenumber` footer with title — the exact combination the issue describes), `avtal.json`, `block_spacing_all.json`.

## Approach

Two small, independent moves and the cleanup they leave behind:

1. **The block owns its page style.** `\makedoctitle` opens with `\clearpage` and `\thispagestyle{empty}`, and the `\thispagestyle{fancy}` at its tail goes. `empty` is LaTeX's standard chrome-free page style; it applies to the page being built when the macro runs, and the `\newpage` at the end ships that page, so the rest of the document keeps `\pagestyle{fancy}` from `klartex-base.cls`. The leading `\clearpage` makes the title page its own page whatever precedes it — the block is a "full-page title" by its schema, and without the break a `title_page` placed after ordinary content would strip the chrome from that content's page too. TeX discards glue and penalties contributed to an empty page, so the `\clearpage` is a no-op at document start and directly after another `title_page`. Setting the style before the content rather than after it means the style is decided for the page the title lands on, not for whichever page the macro's tail happens to run on. This works for every chrome source — predefined slots, per-slot custom sources and a whole-page source — because it is issued from the body, after any preamble; the guarantee is for fancyhdr-based chrome, which is what every source in this repository is — a source that redefines `\ps@empty` or draws through shipout hooks is outside it.
2. **`first_page_header` is removed** from the page-template surface: the `DOCUMENT_SETTINGS` entry (which also removes it from the generated JSON Schema and the loader's key allow-list, `PAGE_TEMPLATE_KEYS`), the `PageTemplate` field and its default, and composition step 5. A payload that still sends the key is rejected by the schema and by the loader with `Unknown page_template key(s): first_page_header` — the same shape as #67's removal of top-level `page_numbers`.
3. Goldens, tests, README/CLAUDE.md and a `CHANGELOG.md` entry under `## Orealiserat` follow.

No Python behaviour beyond the key removal changes; no schema file is edited by hand (the subtree is generated).

## Design Decisions

> Each decision states its provenance: *user decision* (issue text), *existing convention* (where established), or *agent judgment* (open to challenge in the PR). Agent-judgment items are flagged for the PR body.

**D1 — The empty style is set inside `\makedoctitle` (`klartex-titelsida.sty`), at the macro's start, behind a `\clearpage`; not emitted by the Jinja arm.** Options: (a) in the `.sty`: `\clearpage\thispagestyle{empty}` at entry, `\thispagestyle{fancy}` at the tail removed; (b) leave the `.sty` alone and emit the page style from the `title_page` arm in `_block_engine.tex.jinja`; (c) as (a) but without the leading `\clearpage`, keeping today's "no break at entry". Decision: (a). Provenance: *user decision* for the behaviour ("the `title_page` block sets a fully empty page style (header and footer) for its own page"); *agent judgment* for the location and for the leading `\clearpage`. Consequence if wrong: (a) versus (b) is invisible — same PDF; (a) versus (c) is visible only for a `title_page` that is not the first block: with (c) the title shares the page with the preceding content and the `empty` style strips that content's chrome too, with (a) the preceding content ends its page and keeps its chrome. Reverting (a) to (c) is a one-line follow-up. Rationale: the macro already owns the page-style line and the schema calls the block a "full-page title", so the break at entry is the schema's promise made true; the `\clearpage` is a no-op where it matters most (document start, consecutive title pages), so the common layouts do not move. What would make (b) right: a second caller of `\makedoctitle` that wants chrome on its page; none exists. What would make (c) right: a document that deliberately puts a title block mid-page after other content; none is known, and the current output for that case is not a design anyone asked for.

**D2 — Chrome-free applies regardless of chrome source, including custom slot sources and a whole-page source.** Options: (a) unconditional — the block owns its page; (b) skip when a custom source owns a slot, mirroring how step 5 skipped `first_page_header` for a custom header. Decision: (a). Provenance: *user decision* — the issue's "automatically" and "the behavior belongs to the block — the author who places a title page gets the expected look without touching the template"; the custom-source corollary is *agent judgment*. Consequence if wrong: a custom template that wanted its chrome on the title page cannot get it — the author uses a `heading` block instead of `title_page`, or a follow-up adds an opt-out. Rationale: (b) would need a body-level conditional on preamble state and reintroduce the "which mode am I in" logic the slot model just removed; the old behaviour it would preserve (header on the title page) is the bug being fixed. What would make (b) right: a real custom template that prints chrome on its title page on purpose; none is known.

**D3 — `first_page_header` is removed from the API, not kept as an override.** Options: (a) remove the key entirely — schema, loader, `PageTemplate`, composition step 5, `\fancypagestyle{plain}` redefinition; (b) keep it as a header-only override and document that the footer is untouched; (c) generalise it to `first_page_chrome: bool` covering both slots. Decision: (a). Provenance: *agent judgment* — the issue delegates this explicitly ("Whether the API field stays as an override for special cases or is deprecated is decided in planning"), and it leaves the user-facing surface by *user decision* (the template editor will not expose it). Supporting conventions: klartex carries no compatibility shims or aliases — its one consumer is the user's `klartex.se`, whose code does not send the key (verified); #96 retired `narrowmargins` and #67 removed top-level `page_numbers` the same way (schema + loader rejection, no alias, CHANGELOG breaking-change entry). Consequence if wrong: a payload still carrying the key fails loudly with `Unknown page_template key(s): first_page_header` (HTTP 400 with `detail.path == ["page_template"]` in `klartex serve`) until the key is dropped or reinstated in a follow-up — no silent output change, no data at risk. This is a deliberate capability loss, not only cleanup: today the key also gives a document *without* a `title_page` a header-less first page (the footer stays), and after this change that layout has no API expression. Rationale: (b) keeps a knob whose motivating case is now handled by the block and whose name lies about the footer — the issue's own requirement ("must also answer what happens to the footer") rules it out as-is; (c) is a rename and therefore breaks the key anyway, while adding a feature nobody has asked for; the general facility (b) preserves has no known user, and the template editor — the surface the user designs against — will not offer it. What would make (c) right: a document type that needs a chrome-free first page without a `title_page` block — then reinstate as `first_page_chrome` covering both slots, one table entry in `DOCUMENT_SETTINGS`.

**D4 — Composition step 5 disappears, and with it the `\fancypagestyle{plain}` redefinition.** Options: (a) delete the step; (b) keep emitting an unconditional `plain` redefinition "in case". Decision: (a). Provenance: *existing convention* — the composition emits only what a setting asks for, and nothing in the class or the fragments selects `plain` (no `\maketitle`, `titlepage` or `\chapter`). Consequence if wrong: a stray `\thispagestyle{plain}` somewhere would show article's default `plain` (centered page number) — there is none, and the goldens would surface a change. Rationale: dead code in the preamble is exactly what the golden tests exist to keep out. The `page_template_empty_header.tex` golden loses its two `plain` lines in the same commit, as the golden test's docstring prescribes.

**D5 — Page numbering is unchanged: the title page counts, so the first body page reads `Sida 2 av N`.** Options: (a) leave numbering alone; (b) reset or offset the counter so body pages start at 1. Decision: (a). Provenance: *agent judgment*. Consequence if wrong: a cosmetic difference in the footer numbering, fixed by a follow-up (a `\setcounter{page}` after `\newpage` plus a `LastPage` consideration) with no data effect. Rationale: the issue does not ask for it, and today's documents already number this way; changing the counter interacts with `\pageref{LastPage}` and the `auto` page-number mode and deserves its own issue. What would make (b) right: the user asking for body-relative numbering.

**D6 — The CHANGELOG entry is written in the PR, under `## Orealiserat`.** Options: (a) in the PR; (b) at release time only. Decision: (a). Provenance: *user decision* in the issue ("note it in the CHANGELOG when it ships") plus *existing convention* — #67's implementing commit (`9127637`) added its entry under `## Orealiserat` in the PR. Consequence if wrong: an entry moves between commits; nothing else. Two items: under *Breaking changes*, `first_page_header` removed (rejected by schema and loader, no alias); under *Fixes*, `title_page` renders its page without header or footer, a visible change for existing documents that combine `title_page` with a header- or footer-bearing template.

## Risks

- **Visible rendering change for existing documents.** Any document combining `title_page` with a header- or footer-bearing template loses the chrome on its title page. This is the requested behaviour and the issue asks for a CHANGELOG note; there is no opt-out (D2). The three `title_page` fixtures keep compiling; their look changes.
- **Breaking API change.** `first_page_header` goes from accepted to rejected. Mitigated by the loud, pathed error, by #67's identical precedent, and by the verified fact that `klartex.se`'s code never sends it. The `klartex.se` docs that mention it are a follow-up in that repo.
- **`\thispagestyle` placement and long titles.** The style is set before the title content, so it governs the page the title starts on. The schema puts no length limit on the three fields; a title block that overflowed onto a second page would carry chrome there — a multi-page title block is unsupported, not handled. Not a regression: today's tail placement would misplace the style on the same input.
- **The leading `\clearpage` moves a mid-document title page.** A `title_page` after ordinary content now starts on a fresh page instead of continuing the current one. This is the schema's "full-page title" made true, and the three fixtures that carry a `title_page` place it first, so their output moves only in the chrome; it is nonetheless a layout change the CHANGELOG entry names.
- **`empty` versus the class's fancyhdr setup.** `\thispagestyle{empty}` selects LaTeX's own `\ps@empty` for one page; fancyhdr's `\pagestyle{fancy}` remains the document style, so page 2 onward is unaffected. The PDF-level tests in step 6 assert both halves — chrome gone on page 1, present on page 2 — rather than only the absence.
- **Test dependency on `pdftotext`.** The step-6 PDF tests need poppler; CI already requires it for `tests/test_pdf_text_layer.py`, and the skip guard in `ci.yml` covers `xelatex`-tagged tests — make sure the new tests carry the same marker shape as the existing `requires_tools` so a missing tool fails CI rather than skipping silently. Matching the text layer on `Sida 2 av 2` relies on the Swedish strings in `klartex-base.cls` (`\kx@page`, `\kx@of`); the document is rendered with the default `lang`, so they are stable.
- **Golden drift.** Removing step 5 changes the `empty_header` golden; the other goldens must not change. If `letterhead_title` or `logo` diff, something other than step 5 moved.
